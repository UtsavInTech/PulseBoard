# PulseBoard

Behavioral analytics for digital products. PulseBoard turns raw end-user
activity into role-specific insight for Product, Growth, Research and Executive
teams — one dataset, four analytical lenses — with an authenticated AI
assistant that answers questions by querying the same analytics engine the
dashboards use, rather than guessing.

## What it does

Most analytics tools hand every team the same dashboard and let them work out
which half is relevant. PulseBoard starts from the opposite premise: a Product
Manager, a Growth Manager, a Researcher and an Executive are asking genuinely
different questions of the *same* behavioral data, and the product should
answer each of them directly.

The model is:

```
One organization
   └── one digital product
         └── one shared behavioral dataset
               └── four role-specific analytical perspectives
```

Roles change the **lens**, never the data. All four accounts in the demo query
identical rows — a test asserts they return the same `total_events`, and fails
if they ever diverge.

### Four distinct populations

Keeping these apart is the core modelling decision in the project:

| Concept | Table | What it is |
|---|---|---|
| **PulseBoard employees** | `users` | People who sign in and *analyse*. Carry a name, work email, role and organization. |
| **End users** | `end_users` | The customer company's own users, who *generate* the data. Carry age, gender, acquisition source, signup date, country. |
| **Behavioral events** | `events` | What end users did. Org-scoped, with session, category, product, device and browser. |
| **Demo/call leads** | `demo_requests` | Prospects who asked for a demo via the public website assistant. Not analytics data. |

An earlier iteration conflated the first two — the signed-in employee's own
dashboard clicks were being written into the dataset they were analysing, and
their age and gender were displayed as if they were the subject of study.
Employee telemetry now lives in a separate `member_activity` table and never
reaches `/analytics`.

## The demo dataset

`backend/seed.py` generates a synthetic e-commerce marketplace — **Meridian
Retail**, product **Meridian Shop**:

- **260** synthetic end users
- **~4,800** events across **60 days** of history
- **19** event types
- Deterministic: `random.seed(20260829)`, so a reseed reproduces the same shape

### The journey

```
session_started → homepage_viewed → search → category_viewed → product_viewed
→ review_viewed → wishlist_added → add_to_cart → cart_viewed → checkout_started
→ address_added → payment_attempted → purchase_completed
```

with the negative paths that make a funnel realistic: `cart_abandoned`,
`checkout_abandoned`, `payment_failed`, `order_cancelled`, plus `signup`,
`onboarding_complete` and `login`.

### Dimensions

| Dimension | Values |
|---|---|
| Categories | Electronics, Fashion, Home & Kitchen, Beauty, Sports, Books, Grocery |
| Devices | mobile (58%), desktop (34%), tablet (8%) |
| Browsers | Chrome, Safari, Edge, Firefox, Chrome Mobile, Safari Mobile, Samsung Internet |
| Acquisition sources | Organic Search, Paid Social, Direct, Email, Referral |
| Countries | India, US, UK, Germany, Singapore, Australia |

### Planted patterns

The generator does not draw independent random numbers. It applies conversion
multipliers per category, device and channel so the dashboards have something
real to surface:

| Pattern | Mechanism |
|---|---|
| Electronics draws the most views but converts worst | 30% browse share, 0.62× conversion multiplier |
| Home & Kitchen and Grocery convert well on low volume | 1.38× and 1.45× multipliers |
| Mobile carries traffic but abandons checkout | 0.72× checkout multiplier vs desktop's 1.30× |
| Paid Social brings volume without buyers | 26% of users, 0.58× multiplier |
| Email and Referral convert best | 1.42× and 1.30× |
| Review readers add to cart more often | 1.45× boost after `review_viewed` |
| Returning users convert better | 1.42× boost on repeat sessions |
| Payment failures cause real loss | 12% of payment attempts fail |

Exact figures shift slightly with the seed date, so this README deliberately
does not quote specific conversion percentages — read them off the dashboard.

## Role-based dashboards

Each dashboard reads top to bottom as a decision path, not a chart gallery:

**Question → what you can learn → KPIs → filters → what needs attention /
what's working → supporting evidence → collapsed raw-event exploration**

| Role | The question it answers | What it prioritises |
|---|---|---|
| **Product Manager** | What are users using, what are they ignoring, where do they drop off? | Feature adoption, category performance, the marketplace funnel |
| **Growth Manager** | Where do users come from, do they activate, convert and return? | Acquisition channels, channel quality, activation and retention |
| **User Researcher** | How do users behave, and where do they struggle? | Common paths, repeated actions, abandonment, device friction |
| **Executive** | What is happening overall, and what needs attention? | Product health in four numbers, largest leak, cross-role signals |

Every card carries an info popover answering four fixed questions — what it
shows, how it is calculated, why it matters, and a worked example using the
*current* filtered data.

> **On permissions:** a role selects an analytical perspective and the
> suggested questions. It is **not** an access-control boundary — all four
> roles can read the whole organization dataset by design. Access control in
> PulseBoard is at the **organization** level, not the role level.

## Analytics engine

All dashboard numbers come from `compute_analytics()` in
`backend/app/routers/analytics.py`. There is exactly one implementation, and
the AI tools call the same function — the assistant and the charts cannot
disagree.

**Funnels** are progressive intersections: each stage counts users who
completed it *and* every prior stage, so the funnel can only narrow. Counting
stages independently once produced an "Engaged 106.2%" step, because users who
signed up before the window still browsed inside it. A test guards this.

**Breakdowns** are two-stage: how many distinct users a segment reached, and
how many converted. A segment carrying meaningful volume but converting ≥20%
below the average across the breakdown is flagged `attention`; ≥20% above is
`positive`. That flag drives the coloured markers in the UI.

**Insights** are computed per role from the same query — period-over-period
movement, weak and strong segments, largest funnel loss, the review-reader
correlation, payment-failure rate, returning versus new. Nothing is hardcoded
in React; a line is omitted entirely when its data is absent.

**Filters** (date range, age bracket, gender) apply to the base query and
genuinely move every downstream number.

**Caching**: results are cached in Redis for 60 seconds, keyed by organization,
role, window and filters. Redis is optional — the app degrades gracefully to
direct queries if it is unreachable.

## AI architecture

Two separate assistants, deliberately not sharing a code path beyond the OpenAI
client.

### 1. Public website assistant

Unauthenticated, on the marketing site. Answers product questions grounded in
`backend/knowledge/` and captures demo/call requests via a `capture_demo_request`
tool. It has **no access to analytics data**.

| Endpoint | Purpose |
|---|---|
| `GET /ai/status` | Whether the assistant is configured |
| `POST /ai/chat` | Buffered reply |
| `POST /ai/chat/stream` | Server-sent events |
| `POST /ai/demo-request` | Direct lead submission |

### 2. Dashboard analytics assistant

**JWT-required.** Answers analytical questions about the signed-in user's
organization by calling analytics tools.

| Endpoint | Purpose |
|---|---|
| `GET /ai/dashboard/info` | Role, company, role-specific starter questions |
| `POST /ai/dashboard/chat/stream` | Streamed answer with tool use |
| `GET /ai/demo-requests` | Captured leads (JWT-required) |

```
User
 ↓
React  (DashboardAssistant.jsx, fetch + ReadableStream)
 ↓
FastAPI  /ai/dashboard/chat/stream
 ↓
Authentication  (JWT → User → organization_id)
 ↓
AI Assistant  (role-specific system prompt)
 ↓
Analytics Tools  (4 tools, org-bound)
 ↓
Analytics Engine  (compute_analytics)
 ↓
PostgreSQL
```

**The four tools:**

| Tool | Returns |
|---|---|
| `get_analytics_summary` | KPIs, funnel, breakdown, computed insights — delegates to `compute_analytics` |
| `get_daily_activity` | Daily counts with weekday names, plus a SQL-computed weekend/weekday split |
| `get_breakdown` | Volume and conversion by category, device, browser or acquisition source |
| `get_common_paths` | Session transitions, depth, repeated actions, abandonment |

### How grounding is enforced

Prompt instructions alone are not enough, so the constraints are structural:

**Organization scoping.** `org_id` is read from the JWT-resolved `User` object
and bound into the tool runner. No tool parameter accepts an organization — the
model cannot ask for another company's data because there is no field through
which to ask.

**The model never picks the date range.** No tool exposes a date or demographic
parameter. The window comes from the dashboard the user is looking at, sent as
trusted application state and resolved server-side. To read a different span
the model passes a `period` that the server converts:

| `period` | Resolves to |
|---|---|
| `dashboard` *(default)* | Exactly the range the user has selected |
| `previous_period` | The equal-length span immediately before it |
| `this_week` / `last_week` | Monday-to-Sunday weeks |
| `this_month` / `last_month` | Calendar months |

Every result carries `window_used` so the model can state which span a figure
covers. Dates, demographics or an `organization_id` sent by the model are
discarded and reported back to it as ignored.

**Anti-hallucination measures learned from real failures:**

- Distinct user counts are never summed across days — the same user on two days
  is one user. Window-level totals are returned explicitly.
- Weekend/weekday is computed in SQL (`EXTRACT(dow)`), not derived by the model.
- Unknown event names fall back to all events *and say so*, because a filter
  matching nothing reads as "no activity" rather than "wrong filter".
- Today's date and the dataset's actual coverage window are injected into the
  prompt; without them the model invents a date range and reports no data.

The system prompt requires separating observation from interpretation:

> "Paid Social converts at 17.2% against 31.2% for Referral." *(what the data shows)*
> "That suggests Paid Social is worth investigating, though the data alone does
> not establish why it underperforms." *(interpretation, labelled as such)*

Model: `gpt-4.1` via the OpenAI **Responses API**, configurable through
`OPENAI_MODEL`. A reasoning-effort parameter is sent only when the configured
model is a reasoning model (`gpt-5`/`o1`/`o3`/`o4` prefixes), since the gpt-4.x
families reject it.

## Security

| Mechanism | Implementation |
|---|---|
| Password hashing | bcrypt, 12 rounds |
| Authentication | JWT (HS256), `sub` = user id, 24-hour expiry, `HTTPBearer` |
| Authorization | Every analytics and dashboard-AI route depends on `get_current_user` |
| Organization scoping | Derived from the JWT user; never accepted from the client |
| CORS | Explicit origin allow-list, no wildcard, credentials enabled |
| Rate limiting | slowapi, 200 requests/minute per IP |
| Input validation | Pydantic validators on every request body; chat capped at 2,000 chars and 12 history turns |
| OpenAI key | Server-side only, read from environment, never logged or returned |
| Tool argument handling | Model-supplied dates, demographics and org ids are stripped before execution |
| Secrets | `.env` is gitignored; `.env.example` files carry placeholders only |

Errors from upstream degrade to a generic 502 rather than leaking provider
detail, and tool calls log only the tool name and organization id — never the
rows returned.

## Local development

### Prerequisites

- Docker Desktop (running)
- Node.js 20+
- An OpenAI API key — optional; without it the app runs and both assistants
  hide themselves cleanly

### 1. Clone

```bash
git clone https://github.com/UtsavInTech/PulseBoard.git
cd PulseBoard
```

### 2. Environment

```bash
cp .env.example .env
```

Edit `.env` and set at minimum `SECRET_KEY`. Add `OPENAI_API_KEY` to enable the
assistants. `.env` is gitignored — never commit it.

### 3. Start the backend stack

```bash
docker compose up -d postgres redis backend
```

This starts PostgreSQL, Redis and FastAPI. Tables are created on boot.

### 4. Seed the demo data

```bash
docker compose --profile seed run --rm seeder
```

Creates the organization, four employees, 260 end users and ~4,800 events.
Safe to re-run — it clears and regenerates the demo data.

### 5. Start the frontend

```bash
cd frontend
npm install
npm run dev
```

| Service | URL |
|---|---|
| Frontend | http://localhost:5173 |
| Backend | http://localhost:8000 |
| Swagger | http://localhost:8000/docs |
| Health | http://localhost:8000/health |

The port matters: the backend's CORS allow-list names `localhost:5173`
explicitly, so running the frontend elsewhere will fail preflight.

### Everyday commands

```bash
docker compose stop        # stop containers, keep them and all data
docker compose down        # remove containers, KEEP the database volume
docker compose down -v     # remove containers AND DELETE the database
```

`down -v` wipes the `postgres_data` volume — every user, event and captured
lead. Use it only for a clean rebuild, and reseed afterwards.

```bash
docker ps --format "{{.Names}} — {{.Status}}"   # what is running
docker compose logs -f backend                  # follow backend logs
docker compose up -d --build backend            # rebuild after backend changes
```

### Tests

```bash
docker compose run --rm --entrypoint sh backend -c \
  "pip install -q pytest pytest-asyncio httpx && python -m pytest tests -v"
```

**70 tests**, running against in-memory SQLite. They cover authentication,
analytics, role perspectives, shared-dataset invariants, funnel monotonicity,
organization isolation, AI tool scoping, date-context enforcement, SSE
streaming and CORS configuration. No network calls — the OpenAI layer is
stubbed.

### Production build

```bash
cd frontend && npm run build
```

## Environment variables

Configured in `.env` at the repository root (used by Docker Compose) and
`backend/.env` for a bare-metal backend. Both have `.example` templates.

| Variable | Purpose | Default |
|---|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | Database credentials | `postgres` / `postgres` / `analytics_db` |
| `SECRET_KEY` | JWT signing key — **change this** | placeholder |
| `DATABASE_URL` | SQLAlchemy connection string | local Postgres |
| `REDIS_URL` | Cache connection | `redis://localhost:6379` |
| `CORS_ORIGINS` | Allowed origins — JSON array **or** comma-separated | localhost + deployed frontend |
| `FRONTEND_URL` | Extra origin appended to the allow-list | empty |
| `OPENAI_API_KEY` | Enables both assistants | empty (assistants hidden) |
| `OPENAI_MODEL` | Model id | `gpt-4.1` |
| `OPENAI_REASONING_EFFORT` | Only sent for reasoning models | `low` |
| `VITE_API_URL` | Backend URL, **baked in at build time** | `http://localhost:8000` |

> `VITE_*` variables are embedded during `npm run build`, not read at runtime.
> Changing `VITE_API_URL` requires rebuilding the frontend.

**Never commit `OPENAI_API_KEY` or `SECRET_KEY`.** `.gitignore` excludes `.env`
while keeping `.env.example` tracked.

## Production deployment

```
GitHub (main)
   │
   ├── GitHub Actions — ruff lint, pytest, frontend build
   │
   ▼
Railway
   ├── frontend service   (Dockerfile → nginx)
   ├── backend service    (Dockerfile → uvicorn, port 8000)
   ├── PostgreSQL
   └── Redis
```

Frontend and backend are separate Railway services with their own public
domains. Railway builds the Dockerfiles directly and **does not read
`docker-compose.yml`**, so production configuration must come from service
environment variables or code defaults.

Two deployment details worth knowing:

1. **`VITE_API_URL` is a build-time variable.** Changing it in Railway requires
   a rebuild of the frontend service, not just a restart.
2. **CORS must name the deployed frontend origin.** A backend can look
   perfectly healthy — `GET` requests succeed, Swagger loads — while every
   browser call fails, because a simple GET needs no preflight and `OPTIONS`
   returns `400 Disallowed CORS origin`. Set `FRONTEND_URL` on the backend
   service to the frontend's public URL.

## Event tracking

**There is no production SDK.** This repository demonstrates the ingestion and
analytics architecture; it does not ship a packaged client library.

In the demo, events are generated by `backend/seed.py` and written directly to
PostgreSQL. `POST /track` exists but records **PulseBoard employee telemetry**
(which dashboard controls staff use) into `member_activity` — deliberately
separate from the end-user `events` table that `/analytics` reads.

The intended production shape, shown conceptually on the marketing site:

```
Customer website/app
   ↓  pulseboard.track("product_view", { product_id: "P123", category: "electronics" })
Event ingestion API
   ↓
Event storage (PostgreSQL)
   ↓
Analytics engine
   ↓
Role dashboards + AI Analytics Assistant
```

That `track()` call is illustrative. Building the ingestion endpoint and client
library is future work.

## Current limitations

Stated plainly, because an analytics product that overclaims is worse than one
that does less:

- **Synthetic data only.** No real product is connected.
- **No production SDK or public ingestion endpoint.** See above.
- **Event storage is plain PostgreSQL.** No Kafka, no ClickHouse, no streaming
  pipeline. Fine at demo scale; a real deployment at volume would need a
  column-store and an ingestion buffer.
- **Roles are analytical lenses, not permissions.** All four roles can read the
  full organization dataset. There is no RBAC enforcement per role.
- **Schema migrations are hand-rolled.** `ensure_schema()` applies additive
  columns and constraint relaxations idempotently. There is no Alembic; adding
  anything beyond a nullable column needs a real migration tool.
- **No predictive ML, anomaly detection, fraud scoring or billing.** The AI
  assistant interprets computed analytics; it does not model or forecast.
- **Single-tenant demo.** The organization model supports multi-tenancy and
  queries are org-scoped, but only one organization is seeded.
- **The dashboard AI clamps very long windows** to 180 days, so a dashboard
  range longer than that would diverge from what the assistant reads.
- **No LICENSE file yet.**

## Possible future directions

Ingestion API and a lightweight JS SDK · streaming ingestion for higher volume ·
Alembic migrations · per-role permissions where they genuinely matter ·
anomaly detection over the existing event stream · saved reports and alerts.
